### Test A — already-paired state (cc-relay broker hook)

```
$ cat /home/user/.claude/mcp-state/relay.log

✓ Introspect OK: github_login=yhonda-ohishi scope=mcp.read mcp.write
⇒ MCP relay starting (env=staging, user=yhonda-ohishi)
⇒ MCP relay: public URL = https://mcp-staging.ippoan.org/u/yhonda-ohishi/mcp
→ MCP relay: connecting to wss://mcp-staging.ippoan.org/u/yhonda-ohishi/connect as yhonda-ohishi

$ env | grep GITHUB_MCP_URL
GITHUB_MCP_URL=https://mcp-staging.ippoan.org/u/yhonda-ohishi/mcp
```

Note: this container's SessionStart hook is the
**cc-relay broker** (`session-start-cc-relay-broker.sh` from
`yhonda-ohishi/claude-hooks`), not `install-mcp.sh` directly. The broker
reuses the same `github-mcp-server-rs` binary in `relay` mode (with a
pre-staged `$HOME/.config/github-mcp-server-rs/token-staging.json` cache),
so the pair flow never fires. To exercise pair flow we ran `install-mcp.sh`
under a sandbox `$HOME` / `$CLAUDE_PROJECT_DIR` so the real token cache and
real `mcp-state/` were left untouched.

All five sub-assertions for the pair-mode forward path passed:

1. `install-mcp.sh` exited 0.
2. `pair_url` printed to stderr by the hook **and** logged to `pair.log`,
   matching the strict `/mcp/pair/[A-Za-z0-9_-]{30,60}` regex (40-char
   code, no false-positive on the `/mcp/pair/new` POST URL).
3. `pair.pid` written and process alive (polling WS upgrade with
   `Pair-Status: pending`).
4. `mcp-state/url` and `mcp-state/mcp-url` both contain the stable
   per-user URL `https://mcp-staging.ippoan.org/u/yhonda-ohishi/mcp`

5. No re-download triggered (`tag=dev-11` matched `$BIN.tag`, embedded
   tag matched).

The pair process was killed during cleanup to avoid leaking a live
`pair_code` claim against staging. The minted pair_code remains valid
on the auth-worker side for ~5 min then auto-expires.

## Note 1 — tool count discrepancy

Task spec said 40 tools. Actual:

- Binary source has **43 `#[tool]` attribute occurrences** across
  `src/mcp_server.rs` (2: `whoami`, `list_repos`) and `src/tools/*.rs`
  (issues=10, projects=8, actions=6, repository=4, branches=3,
  releases=3, pulls=3, commits=2, logs=2).
- This Claude session's deferred-tool list surfaces **38 tools** under
  the `mcp__72d6cc20-9f30-46e2-ac4f-cf3736a87a7f__` MCP-server prefix
  (the one bound to `$GITHUB_MCP_URL`).

The 5-tool gap between binary source and surfaced-in-Claude is probably:
- 2 tools are `whoami` / `list_repos` which Claude may filter out of the
  exposed list, AND
- 3 tools may be guarded by a feature flag / not yet wired into the
  `rmcp` registration path.

A 38-vs-43-vs-40 spread is **not a regression** — pair flow itself
behaves identically — but worth tracing in a separate ticket. Suggested
follow-up: dump the binary's actual `tools/list` JSON-RPC response (e.g.
by running `pair --auth-base wt-quick.example` against a local
auth-worker) and diff against the `#[tool]` set.

## Note 2 — browser-click portion not exercised

A non-interactive CCoW container cannot tap the pair link surfaced in
Test D. To complete the full forward path:

1. A human re-runs Test D in a CCoW session of their own.
2. Within 5 min, taps the surfaced
   `https://auth-staging.ippoan.org/mcp/pair/<code>` URL in any browser
   (mobile Safari / Chrome included — the auth.ippoan.org session
   cookie is sticky and platform-agnostic; see the user-asked Q in the
   driving session).
3. Verifies `pair.log` gains `✓ pair: WS upgrade accepted` within ~5s.
4. Verifies the registered `$GITHUB_MCP_URL` in Claude Code Web's MCP
   entry now responds to `tools/list` with 38–43 tools (per Note 1).

For mobile specifically: nothing about pair flow requires desktop. The
URL is a normal HTTPS link, the auth.ippoan.org cookie session works
identically on mobile browsers, and the bridge runs server-side
(`mcp-staging.ippoan.org` Cloudflare Worker) so the phone's browser is
not the long-lived endpoint.
